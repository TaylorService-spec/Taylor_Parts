## 1. The three operations are not the same thing, and only one is proposed here

| Operation | Transport | Available now? | Proposed here? |
|---|---|---|---|
| **PUSH BRANCH** | Git over SSH | **YES** — verified, `git ls-remote --heads origin main` → `64008d5a` | **Yes, pending Owner authorization** |
| **OPEN PR** | GitHub REST API | **NO** — `gh auth status`: not logged into any host | No |
| **CHECK CI** | GitHub REST API | **NO** — same | No |

This program has been reporting a blanket `GITHUB_AUTH_REQUIRED`, which conflated all three. **Git
transport is not blocked. Only the API is.** Correcting it forward.

## 2. Pushing a branch triggers no CI and cannot deploy — measured, not assumed

Every workflow in `.github/workflows/` at the baseline was parsed:

| Trigger shape | Count |
|---|---|
| `push` scoped to `branches: [main]` (plus path filters) | **135** |
| `push` with **no** branch filter — would fire on any branch | **0** |
| `pull_request` only, no `push` | **9** |
| **Total workflows** | **144** |

`deploy-field-ops.yml` is `push` → `branches: [main]` only. **So pushing a feature branch starts no
workflow run, consumes no Actions minutes, and cannot reach a deploy.** CI begins only when a PR is
opened (which needs the API) or when something lands on `main` (which needs a merge).

That makes push about as low-consequence as a remote operation gets. The reason to ask anyway is that it
is still outward-facing: 60 new refs appear in a repository other people can see.

## 6. Recommended form of the push

- `git push origin <branch>:<branch>` per branch, **no force, no `--tags`**, never to `main`.
- **Fast-forward only into new refs.** Every proposed ref is absent at the remote (verified by SHA), so no
  push in this set can overwrite anything. `rpt/client-outcome-honesty` is **excluded** — already there.
- Push **Tier 1 first**, confirm the refs, then the later tiers. That way the irreplaceable material is
  safe before anything with a code file moves.
- **Do not open any PR**, even when the API becomes available, until the Owner says which branches become
  PRs and in what order — §4 of the extension forbids mixing Tier-2 work into a normal correctness PR, and
  that discipline is easier to hold before PRs exist than after.

## 7. What this plan does NOT establish

- **That any pushed branch passes its tests at `64008d5a`.** None has been re-proven after rebase.
- **That 60 is the complete at-risk set.** It is complete for the branches this program created and
  tracked. The repository holds **1,631** local branches; the other ~1,570 were not surveyed and some may
  also be local-only. **UNPROVEN**, and out of scope here.
- **Anything about PR or CI state.** Needs the API.
- **That the remote is a sufficient backup.** It is one copy in one place, and it is the same account.
