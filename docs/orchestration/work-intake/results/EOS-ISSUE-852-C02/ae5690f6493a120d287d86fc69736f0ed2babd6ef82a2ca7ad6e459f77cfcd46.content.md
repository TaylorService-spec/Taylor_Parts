### Findings

**1. MEDIUM — Post-commit inventory side effects have no durable retry if the Function instance dies between transaction commit and the trigger call**
- `functions/src/transitionWorkOrder.ts:130-133`, `functions/src/inventoryService.ts:248-275`
- The status transition commits inside `db.runTransaction(...)`; `triggerInventoryEffects()` runs strictly after, per the file's own header comment. It's idempotent per-call (`isStateProcessed`/`markStateProcessed` keyed by `(workOrderId, state)`) and swallows its own errors into `recordFailure`. But if the Function instance dies *before* that call ever executes (recycle/OOM/timeout in the gap between commit and line 133), the WO's `status` has already durably advanced but `reserveParts`/`consumeParts`/`releaseParts` never ran — and no `inventory_sync_status` entry, not even a `failures` record, exists to flag it, since `recordFailure` is only reached if the trigger actually started. A client retry doesn't help: the retried transition is rejected by `canTransition` because status already moved. `inventoryService.ts:256-262`'s own comment confirms recovery here is an acknowledged manual/admin action, not automated — and there's currently no signal telling an operator it's needed.

**2. LOW/INFORMATIONAL — `createWorkOrder` idempotency replay doesn't validate the retried payload matches the original**
- `functions/src/createWorkOrder.ts:110-120`, `functions/src/workOrderCreateMath.ts:10-13`
- The replay-guard id is `sha256(actorUid|customerId|locationId|idempotencyKey)` — it excludes `priority`/`severity`/`type`/`complaint`. A retry reusing the same key with different field values silently returns the original WO with no error, only a `replayed: true` flag. The header comment acknowledges this is an accepted "paired dependency" on client key discipline (same tradeoff finance callables already accept), so this is a known design choice, not an oversight — flagged for completeness since there's no server-side backstop if that discipline slips.
