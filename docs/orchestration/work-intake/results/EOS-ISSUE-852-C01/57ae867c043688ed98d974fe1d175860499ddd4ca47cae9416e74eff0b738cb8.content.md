## Sector 01 — Inventory integrity + transfer/receiving flows

**Scope note**: assigned path `functions/src/receiving` doesn't exist; the real directory is `functions/src/inventoryReceiving`. Analyzed that plus `functions/src/inventoryService.ts` as assigned. No dedicated transfer command exists anywhere in `functions/src` yet.

**High** — Non-atomic ledger-write + processed-marker in `triggerInventoryEffects()` (`functions/src/inventoryService.ts:263-275`). `trigger(workOrderId)` runs its own transaction writing RESERVED/RELEASED/CONSUMED entries via `writeLedgerEntry()` (lines 91-97, no idempotency key, always a new doc ref); `markStateProcessed()` is a separate later write. A crash/error between those two lets `isStateProcessed()` return false on retry, re-running `trigger()` and duplicating ledger entries. `inventoryEffectDetection.ts` (23-27, 152) documents and detects the "silent miss" half of this but its own comments confirm the retry remediation doesn't guard against the double-apply case where the ledger write already succeeded.

**Medium** — Two independently-evolving writers share `inventory_transactions` with disjoint read paths. `getAvailableQuantity()` (`inventoryService.ts:47-61`) only sums RESERVED/RELEASED against the static catalog baseline; it has no knowledge of the newer RECEIVED/TRANSFER_IN/TRANSFER_OUT schema (`operationalMovementTypes.ts:12-16`) that `receiveInventoryStockCommand.ts` (184-197) stages into the same collection. Dormant today (capability registered-but-ungranted, `receivingCallableWiring.ts:4,30`), but merged and load-bearing — will activate silently once granted, with received stock never affecting reservation availability. Any future transfer command inherits the same blind spot.

**Low** — Stale header comment in `receiveInventoryStockCommand.ts` (lines 1-4) claims it's "NOT exported from functions/src/index.ts; no callable" — `index.ts:157-169` does export it (aliased via `receivingCallables.ts`). Doc-drift, not a functional bug.

**Clean**: `receiveInventoryStock()` itself is well-governed — atomic, idempotent via deterministic content-addressed keys, commit-time authorization, sanitized errors, extensively tested.
