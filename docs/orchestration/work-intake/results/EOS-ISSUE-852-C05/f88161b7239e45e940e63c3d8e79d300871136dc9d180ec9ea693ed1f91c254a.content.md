### Findings

**1. LOW — `jobWorkflow.js`'s client-side transition check is role-blind; it permits a technician-initiated job completion that `firestore.rules` would reject, but no live call site currently exercises that path**
- `field-ops-app-vite/src/domain/jobWorkflow.js:3-12` (`canTransitionJob`), `field-ops-app-vite/src/domain/jobActions.js:44-87` (`updateJobStatus`), `firestore.rules:299-321,351-361`
- Rules gate `fieldops_jobs` completion two ways: admin/dispatcher may do any `isValidJobTransition` (including `in_progress → complete`), while a technician may perform *only* `assigned → in_progress` (`isTechnicianJobTransition`) — direct client completion is explicitly denied for technicians, reserved for the trusted `completeAssignedJob` callable (per the Rules' own comment at line 345-350).
- Client-side `canTransitionJob()` has no role parameter — it's a flat state machine (`in_progress → complete` is allowed for any caller). `updateJobStatus()` in `jobActions.js` calls it directly and, on a completion transition, also `tx.update(techRef, { status: AVAILABLE })` on the technician doc — a write Rules restrict to admin/dispatcher only (line 388-389 comment: "a technician holds NO direct write on this collection").
- Today this is dead code from a technician-abuse standpoint: `updateJobStatus` has no live UI call site (grep across `field-ops-app-vite` finds it referenced only in comments and `test/completionFlow.test.mjs`; `ControlTower`/`WorkOrderActions.jsx` mention it only in comments, not calls). So the mismatch fails closed today — a stray call would throw `permission-denied` mid-transaction rather than silently succeed. But the client function offers no earlier guard, so a future feature that wires `updateJobStatus` into technician-facing Field Mode UI would ship a broken "Complete Job" button (or worse, rely on the transaction failure as its only defense) rather than getting a clear client-side rejection.
