## EOS-ISSUE-852-C03 — Sector 03: Dispatch/technician workflow + assignment logic

**Scope read**: work item scope names `functions/src/dispatch` and `src/features/dispatch`, neither of which exist in this repo — the actual dispatch/assignment surface lives at `field-ops-app-vite/src/modules/dispatch/Dispatch.jsx`, `field-ops-app-vite/src/modules/dispatcherBoard/*`, `field-ops-app-vite/src/domain/{dispatchScoring.js,jobActions.js,technicianRecommendationEngine.ts}`, `functions/src/{transitionWorkOrder.ts,completeAssignedJob.ts}`, and the `fieldops_jobs`/`fieldops_wos`/`fieldops_technicians` rules in `firestore.rules`. Profile is `READ_ONLY_ANALYSIS` with `capabilities: []`; no writes were made anywhere in the repo — this response is the deliverable.

### Findings

**1. MEDIUM — The governed Dispatch transition writes `assignedTechId` with no server-side check that the technician exists or is available, dropping a guard the legacy path had**
- `functions/src/transitionWorkOrder.ts:64-66, 97-118`
- `assertValidInput` only requires `assignedTechId` to be *present*; the transaction body never reads `fieldops_technicians/{assignedTechId}` — it just writes whatever string the client sent straight onto the Work Order (`payload.assignedTechId = assignedTechId`). There is no existence check and no re-check that the technician's `status` is `available` at commit time.
- Contrast with the now-unused legacy `assignJob()` (`field-ops-app-vite/src/domain/jobActions.js:106-124`), which reads the technician doc *inside the transaction* and throws `AssignmentConflictError` if `!techSnap.exists() || techSnap.data().status !== TECH_STATUS.AVAILABLE` — exactly the guard that's now missing from the path every dispatch surface (`Dispatch.jsx:88`, `DispatcherBoard.jsx:110`) actually calls.
- Practical effect: two dispatchers (or one dispatcher double-clicking two different job cards) can dispatch two different Work Orders to the same technician concurrently — both `transitionWorkOrder` calls succeed independently because each only re-checks its *own* Work Order's status (`canTransition`/`getAllowedActions`), never the target technician's state. `fieldops_wos` rules (`firestore.rules:476-480`) close all client writes, so there's no rules-level backstop either — this function is the only gate. A typo'd or nonexistent `assignedTechId` is also silently accepted and persisted.
- The UI's own client-side filter (`Dispatch.jsx:144`: `technicians.filter(t => t.status === AVAILABLE)`) is cosmetic against this race, not a substitute for a server check.

**2. MEDIUM — A dead but still fully-authorized legacy write path (`assignJob()`) duplicates the governed Dispatch transition with different (weaker) audit behavior**
- `field-ops-app-vite/src/domain/jobActions.js:89-131`, `firestore.rules:340-361`
- Grepping the whole app for call sites of `assignJob(` turns up zero live callers — every remaining reference is a comment ("Dispatch.jsx: the legacy assignJob() client transaction... is no longer used here"; `dispatchScoring.js:128`). But `firestore.rules`'s `fieldops_jobs` `update` rule still authorizes it unconditionally for any admin/dispatcher performing "a previously-approved lifecycle/assignment change" (rule comment: "PR-2 contract, unchanged here") — this wasn't retired, just stopped being called from the current UI.
- Unlike the governed `fieldops_wos`/`transitionWorkOrder` path and unlike `completeAssignedJob.ts`'s audit-doubles-as-idempotency pattern, this path is a bare client `runTransaction` with no audit event and no idempotency key at all. If it's ever re-wired to a UI element (or invoked directly via the console by an admin/dispatcher session, which the rules permit today), assignments made through it would leave no audit trail and bypass whatever downstream logic now depends on the `fieldops_wos` engine being the sole source of truth for assignment — reintroducing dual-write authority over "who is assigned" without anyone having decided that on purpose.

**3. LOW/INFORMATIONAL — Recommendation engines are correctly read-only and non-authoritative, but the two independently-weighted scoring implementations already exist in parallel with no shared source**
- `field-ops-app-vite/src/domain/dispatchScoring.js` (weights: urgency 0.35 / availability 0.3 / workloadBalance 0.25 / workOrderPriority 0.1) and `field-ops-app-vite/src/domain/technicianRecommendationEngine.ts` (weights: workload 0.4 / experienceAffinity 0.25 / availability 0.2 / territoryMatch 0.15) both compute a 0–100 "who should get this job" score from different factor sets and different weights, feeding different UI surfaces (`ControlTower`/`AtRiskPanel` vs. `DispatcherBoard`). Neither writes anything (confirmed: no Firestore calls, no `assignJob`/`transitionWorkOrder` invocation in either file) so this isn't a correctness bug, but a dispatcher moving between the two boards would see two different "recommended technician" answers for the same job with no documented reconciliation — worth a note if a single canonical recommendation is ever expected.

### Verified sound (no finding)
- `functions/src/completeAssignedJob.ts` — technician-only, server-resolved identity, exact-ownership check (`job.technicianId !== technicianId`), state-machine guard, and an audit-event-as-idempotency-key pattern that also correctly handles idempotency-key reuse-for-a-different-operation as a distinct denial rather than silently dropping or overwriting. No issues found.
- `transitionWorkOrder.ts`'s action-based (never raw-status) input, transactional re-read of current status, and role/`isOwnAssignment`-gated `getAllowedActions` check together prevent a client from smuggling an arbitrary transition or acting outside its role — sound apart from Finding 1.
- `dispatchScoring.js` and `technicianRecommendationEngine.ts` are both genuinely pure/derived-only (own header comments explicitly disclaim any write path, and no write call sites were found) — Dispatch.jsx and DispatcherBoard.jsx remain the only places an assignment is actually committed.
- `EmployeeAssignmentPicker.jsx`/`useAssignableEmployees.js` — out of scope for this sector: by their own header comments they are a not-yet-adopted generic assignment primitive with "ZERO production consumers," unrelated to the technician-dispatch flow reviewed here.
