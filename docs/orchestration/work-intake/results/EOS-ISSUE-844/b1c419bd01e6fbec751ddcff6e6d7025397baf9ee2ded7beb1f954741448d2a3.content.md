## EOS-ISSUE-844: Execution Capability Profiles — Analysis Report

**Source:** `docs/orchestration/lib/executionProfiles.mjs` (verified against current repo state, 2026-08-13)

### Purpose
Replaces the prior hard-coded 40-turn / single-allowlist assumption (root cause behind #834/#835/#836/#837) with four explicit, fail-closed task-class profiles. Each is a self-contained authority envelope enforced structurally at construction via `assertProfileInvariants` — not by convention.

### The four profiles

| Profile | Turn ceiling | Write | Worktree | Integration | Capability envelope |
|---|---|---|---|---|---|
| **READ_ONLY_ANALYSIS** | 40 | ✗ | ✗ | ✗ | `Read`/`Grep`/`Glob` + read-only git (`status`, `diff`, `log`, `show`, `rev-parse`, `ls-files`). This is the **DEFAULT_PROFILE** — least-privilege fallback. |
| **READ_ONLY_VERIFY** | 60 | ✗ | ✗ | ✗ | Adds test/build/lint commands (`node --test`, `npm test`/`run test`/`run build`/`run lint`, `npx tsc`) on top of analysis tools. |
| **PATCH_PRODUCER** | 80 | ✓ | ✓ | ✗ | Adds `Edit`/`Write` + isolated-worktree/patch commands (`git worktree`, `checkout`, `add`, `stash`, `apply`, `diff`, `sha256sum`). Explicitly forbidden from carrying `git push`, `gh pr create`, `grantRole`/`revokeRole` — producer authority sits strictly below integration. |
| **GOVERNED_INTEGRATION** | 100 | ✓ | ✓ | ✓ | Superset of PATCH_PRODUCER plus `git push` and `gh pr create` only. Never merge or deploy. |

### Structural invariants (enforced, not conventional)
- `permissionMode` is always `"dontAsk"` — `bypassPermissions` is unrepresentable.
- Bash is always an explicit allowlist; unrestricted `Bash`/`Bash(*)` is rejected via regex check.
- No profile — including GOVERNED_INTEGRATION — may carry merge, deploy, or credential-read authority (`gh pr merge`, `firebase deploy`, `gcloud`, `npm publish`, force-push, secret/env access markers).
- Privilege ordering is `READ_ONLY_ANALYSIS(0) < READ_ONLY_VERIFY(1) < PATCH_PRODUCER(2) < GOVERNED_INTEGRATION(3)`.
- `resolveExecutionProfile()` implements two-key governance: a `requestedProfile` (worker-declared need) can never self-escalate — it only takes effect if a separately Owner-authored `authorizedProfile` grants rank ≥ requested. Unauthorized escalation fails closed to `READ_ONLY_ANALYSIS`. Unknown profile names on either side also fail closed.

### Assessment
The design correctly separates *declared need* from *governed grant*, and turn ceilings scale monotonically with authority (40→60→80→100), bounding worst-case runaway cost per privilege tier. All four profiles pass their own `assertProfileInvariants` check at module load — this is self-verifying at import time, not just documentation.
