## EOS-ISSUE-852-C09 — Sector 09: UI/UX workflow correctness + error handling

**Scope**: `field-ops-app-vite/src` (read-only analysis, no repo writes).

### Findings

**1. HIGH — `ErrorBoundary` has no reset mechanism; any single render crash permanently kills the whole app session**
`field-ops-app-vite/src/components/ErrorBoundary.jsx:9-28`, mounted once at `field-ops-app-vite/src/main.jsx:9-17` wrapping the entire app (`<ErrorBoundary><AuthProvider><App/></AuthProvider></ErrorBoundary>`), with no nested/route-scoped boundaries anywhere else in `src`.
```jsx
static getDerivedStateFromError(error) {
  return { hasError: true, error };
}
componentDidCatch(error, info) {
  console.error("UI Crash:", error, info);
}
render() {
  if (this.state.hasError) {
    return <div style={{ padding: 20 }}><h2>Something went wrong</h2><pre>{String(this.state.error)}</pre></div>;
  }
  return this.props.children;
}
```
Once `hasError` flips true it never flips back — no "Try again" action, no key-based remount, no reset on route/prop change. A single render-phase exception anywhere in the app (malformed Firestore doc, null-deref edge case) takes down the entire session; recovery requires a full page reload, discarding any in-progress form state. The fallback also renders `String(error)` — potentially raw stack/message — to the user.
→ Fix: add a reset callback (button + key-based remount) and scope boundaries per route/major panel instead of one global boundary.

**2. MEDIUM — Raw Firebase/Functions error text leaks to users in several modules, contradicting the codebase's own safe-error convention**
`field-ops-app-vite/src/modules/inventory/PartDetail.jsx:377,451,531,677,831,1115`; `field-ops-app-vite/src/modules/inventoryRole/PartsAssociateHome.jsx:105,298`; `field-ops-app-vite/src/modules/inventoryRole/PartsManagerHome.jsx:72`; `field-ops-app-vite/src/modules/inventoryRole/WarehouseManagerHome.jsx:208`; `field-ops-app-vite/src/modules/inventory/PartsList.jsx:501`; `field-ops-app-vite/src/modules/technicianDashboard/ExecutionCapture.jsx:41,57`; `field-ops-app-vite/src/modules/technicianDashboard/PerformanceSnapshot.jsx:44`

```js
} catch (err) {
  setError(err.message);   // PartDetail.jsx:377, ExecutionCapture.jsx:41/57, etc.

```
`domain/workflowActionError.js` explicitly documents and enforces the opposite convention ("It NEVER surfaces a raw err.message, a Firebase/Functions code, a stack, a UID, or a document id") — correctly followed by `NewJobModal.jsx`, `AccountForm.jsx`, `WorkOrderActions.jsx`, `TechnicianWorkOrderActions.jsx`, and `ConfirmDialog.jsx` via `jobSaveErrorMessage`/`accountSaveErrorMessage`/`workflowActionErrorMessage`. → Fix: route these `catch` blocks through the existing safe-mapping helpers instead of `err.message`.

**3. LOW — Some submit handlers clear the "submitting" flag only in `catch`, not `finally`, risking a permanently-stuck button**
`field-ops-app-vite/src/modules/inventory/PartDetail.jsx:369-380`; `field-ops-app-vite/src/modules/inventoryRole/PartsAssociateHome.jsx:99-108`
```jsx
async function handleAssign(e) {
  e.preventDefault();
  setSubmitting(true);
  setError(null);
  try {
    await assignReorderRequest(request.id, { assignedToUserId });
    onAssigned();
  } catch (err) {
    setError(err.message);
    setSubmitting(false);
  }
}
```
Unlike `NewJobModal.jsx`/`AccountForm.jsx`/`WorkOrderActions.jsx` (all use `finally { setSubmitting(false) }`), these reset `submitting` only on the `catch` path, relying on the success path to unmount/replace the component. If `onAssigned()` itself throws, or the component doesn't unmount immediately, the button stays disabled indefinitely with no error and no retry short of a page reload.
→ Fix: move the reset into a `finally` block, matching the rest of the codebase.
