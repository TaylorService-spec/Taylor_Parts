## EOS-ISSUE-852-C06 — Sector 06: Cloud Functions / callables / auth boundaries

**Scope**: `functions/src/callerContext.ts` + `functions/src/access/` (17 files), cross-referenced against the deployed callables that consume `getCallerContext` (`createWorkOrder.ts`, `transitionWorkOrder.ts`, `updateWorkOrderExecutionData.ts`, `getWorkOrderFieldContext.ts`, `completeAssignedJob.ts`) and the `firestore.rules` boundary that makes server-side role trust valid in the first place.

### Findings

No security-relevant findings. This is an unusually well-defended surface — every deployed callable follows the identical pattern: `request.auth.uid` is the only source of actor identity, role/technicianId are resolved server-side via `getCallerContext` (never trusted from `request.data`), ownership is re-verified inside the same Firestore transaction that performs the write, and denials are distinguished from "genuinely nothing here" states.

### Verified sound (no finding)
- **Trust root**: `getCallerContext()` (`functions/src/callerContext.ts:15-22`) reads `users/{uid}.role`/`technicianId` via the Admin SDK. `firestore.rules:397-400` (`match /users/{userId} { allow write: if false; }`) makes this field client-immutable — the entire callable layer's role trust is sound only because of this rule, and it holds.
- **Actor-identity discipline**: every callable in scope (`createWorkOrder`, `transitionWorkOrder`, `updateWorkOrderExecutionData`, `completeAssignedJob`, `getWorkOrderFieldContext`, and the not-yet-deployed `accessCommandCallables.ts` six adapters) derives `actorUid` exclusively from `request.auth.uid`, never from `request.data`. `completeAssignedJob.ts:71-98` even structurally rejects any unknown input field (so a client can't smuggle a `technicianId`/`role` override).
- **Ownership re-verified server-side, inside the transaction**: `updateWorkOrderExecutionData.ts:123` and `completeAssignedJob.ts:270` both compare the resolved `caller.technicianId` against the document's own `assignedTechId`/`technicianId` field read inside the same `runTransaction`, not a value cached earlier — no TOCTOU gap.
- **`getWorkOrderFieldContext.ts`** (customer/location display projection for technicians): ids read to satisfy the projection come only from the Work Order the caller is already authorized to read (`authorizeFieldContextRead`, line 96-129), never from client-supplied `customerId`/`locationId` — closes the obvious "turn a display projection into an arbitrary-record reader" path.
- **Error-message hygiene**: `accessCommandCallables.ts`'s `mapCommandError` (line 35-120) and `legacyAuthorizationSurface.ts`'s adjacent `adminCredentialCallables.ts` (`mapError`, line 23-63) both deliberately generalize internal error detail (resolver denial reasons, Firestore paths, reset tokens) into safe, generic `HttpsError` messages — audited case-by-case in comments, not a blanket catch-all that risks under- or over-disclosure.
- **Dormant/non-deployed surfaces correctly gated**: `accessCommandCallables.ts` (grantRole/revokeRole/etc.) and `adminCredentialCallables.ts` (password-reset) are explicitly documented as exported-but-not-deployed / fail-closed-on-unconfigured-send, pending separate Owner production authorization — consistent with what's actually wired.
- **`legacyAuthorizationSurface.ts`** is confirmed inert (pure data, not imported by any runtime authorization path, CI-enforced via a rules-reparse test) — matches its own header claim.
- **One pre-existing, already self-documented gap** (not new, not reported as a finding): `updateWorkOrderExecutionData.ts:26-31` and `createWorkOrder.ts:24-30` both treat `idempotencyKey` as optional for backward client compatibility, meaning a keyless call has no replay protection — this is called out in-line as intentional deploy-safety debt with a named paired dependency (client must start sending a stable key), not an oversight.
