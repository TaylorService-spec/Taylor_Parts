CORRECTION (self-reported; the first version of this file was wrong)
  The first version claimed builds from 2d08e2e and from the preparation branch are
  "byte-identical". That measurement was real but MISATTRIBUTED: at the time it was
  taken, the preparation branch's changes were still UNCOMMITTED, so the worktree HEAD
  was itself 2d08e2e. Once the preparation work was committed, the bundle changed.

  ROOT CAUSE -- the build is COMMIT-DEPENDENT BY DESIGN. vite.config.js injects
    __APP_COMMIT__ = JSON.stringify(execSync('git rev-parse --short HEAD'))
  (added by INV-CONVERGENCE-E Stage A as the deterministic build identifier; it falls
  back to "unknown", which the shadow-parity core treats as BLOCKED_INCOMPLETE_INPUT
  rather than a false PASS). So EVERY distinct commit produces a distinct bundle hash.
  That is intended: the deployed build id must identify the deployed commit.

MEASURED RELATIONSHIP (exact, reproducible)

    assets/index-DadxuIqI.js  sha256 02a667c4df2a9fdc77bc37ce35c405be43feeb3461f5097ce5342032be557722
  Build at HEAD = 87d489c (preparation branch, short "87d489c"):
    assets/index-tezVCxVH.js  sha256 42d6855889be09dfb84e8b39f58e7770a4647b77c53ce608872e17a3cacd8757

  The injected short SHA occurs EXACTLY ONCE in the bundle. Substituting that single
  occurrence ("87d489c" -> "2d08e2e") in the preparation build reproduces the 2d08e2e
  build hash EXACTLY:
    sed 's/87d489c/2d08e2e/g' index-tezVCxVH.js  ->  sha256 02a667c4...557722   (equal)

  CONCLUSION: the two bundles differ ONLY in the one-occurrence build-identifier
  string. The application code is identical -- the preparation PR adds only scripts/,
  test/, and docs/ paths, none of which is imported by src/ or participates in the
  Vite bundle graph.

CONSEQUENCES FOR THE RUNBOOK
  1. The operator's build at AUTHORIZED_COMMIT will produce a DIFFERENT asset filename
     and hash from both values above. That is EXPECTED, not a defect.
  2. No fixed asset hash may be pre-registered in this package as the expected
     deployed artifact. Step 7 is the governing check: it binds the LIVE bytes to the
     operator's OWN Cloud Shell build manifest (local-dist-manifest.sha256) with an
     exact-equality assertion and a hard STOP on mismatch. That check is unaffected by
     the build id, because both sides of the comparison come from the same build.
  3. Cross-checking the deployed build id: the deployed bundle should contain the
     short SHA of AUTHORIZED_COMMIT. This is a useful confirmation that the deployed
     artifact came from the authorized commit.
